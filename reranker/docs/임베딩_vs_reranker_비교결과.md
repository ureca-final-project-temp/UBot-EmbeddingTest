# 임베딩 단독 vs 임베딩+Reranker 비교 테스트 결과

**테스트 환경**: BGE-M3 임베딩(1단계) + BGE reranker v2-m3 / Jina reranker v2(2단계), FAQ 1,000개, 테스트 쿼리 57개(FAQ_RAG 의도만, MAP_API 3개 제외)

---

## 1. 지표 설명

- **Top-1(단독/rerank)**: 검색 결과 1등이 정답인 비율. "단독"은 임베딩만으로 검색한 결과, "rerank"는 그 결과를 reranker로 재정렬한 뒤의 결과
- **MRR(단독/rerank)**: 정답이 몇 등에 있었는지를 반영한 평균 점수(1등=1점, 2등=0.5점, 3등=0.33점...). 1에 가까울수록 정답을 앞쪽에 잘 배치했다는 뜻
- **개선**: reranker가 순위를 정답 쪽으로 더 좋게 바꾼 쿼리 개수
- **악화**: reranker가 순위를 오히려 더 나쁘게 바꾼 쿼리 개수
- **1단계 실패**: 1단계(임베딩)가 애초에 정답을 Top-K 후보 밖으로 뒀던 개수. reranker는 Top-K 후보만 보므로 이 경우는 reranker가 손쓸 수 없는, reranker 책임이 아닌 실패
- **top_k**: 1단계 검색 결과 중 몇 개까지를 reranker에게 넘겨 재정렬시킬지 정하는 값

## 3. 핵심 발견

- **BGE reranker는 top_k=10에서 최초로 단독 임베딩(MRR 0.846)을 넘어섬 (0.862)**
- **FAQ 100개 기준 테스트에서는 reranker가 계속 손해였으나, FAQ 1,000개로 늘리자 결과가 반대로 바뀜**
  - FAQ 100개: 단독 0.869 → +BGE reranker 0.860 (손해)
  - FAQ 1,000개: 단독 0.846 → +BGE reranker 0.862 (이득)
  - 해석: FAQ 규모가 커질수록 1단계 임베딩 검색의 변별력이 떨어지고, 이때 reranker의 정밀 재정렬 효과가 커짐
- **top_k=10 이후로는 개선 효과가 정체됨**: top_k 10/15/20 모두 개선 건수 10건으로 동일 → top_k=10 시점에 1단계 실패(stage1_miss)가 이미 0이 되어, 더 넓혀도 추가로 구제할 정답이 없음
- **top_k를 필요 이상으로 늘리면 오히려 악화 건수만 증가**: BGE는 4→5건, Jina는 8→11→12건으로 계속 증가
- **Jina reranker는 전 구간에서 BGE reranker보다 낮은 성능**, top_k가 클수록 격차가 더 벌어짐

## 4. 카테고리별 결과 (top_k=10, BGE reranker 기준)

| 카테고리 | Top-1(단독) | Top-1(rerank) | 변화 |
|---|---|---|---|
| Easy | 77.8% | 88.9% | 개선 |
| Hard | 66.7% | 55.6% | 악화 |
| Medium | 44.4% | 44.4% | 동일 (MRR은 0.601→0.657로 개선) |
| 구어체 | 100% | 100% | 동일 (이미 만점) |
| 긴질문 | 70.0% | 70.0% | 동일 (MRR은 0.825→0.833으로 소폭 개선) |
| 오타 | 100% | 100% | 동일 (이미 만점) |

- Easy 카테고리에서 가장 뚜렷한 개선
- Hard 카테고리는 오히려 악화 — 복잡한 의도의 질문에서는 reranker가 여전히 취약

## 5. 속도 / 리소스

| 항목 | 값 |
|---|---|
| FAQ 1,000개 코퍼스 임베딩 시간 | 0.86초 (1회성, top_k와 무관) |
| 쿼리 1개 임베딩 평균 시간 | 약 0.011~0.033초 |
| BGE reranker 재정렬 시간 (top_k=10 기준) | 약 0.019초 |
| BGE reranker 재정렬 시간 (top_k=20 기준) | 약 0.033초 |

- top_k가 커질수록 reranker 처리 시간은 선형적으로 증가
- top_k=10을 넘겨도 정확도 이득이 없으므로, 불필요한 지연시간만 추가되는 셈
